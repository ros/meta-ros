# meta-ros Layer Audit

You are auditing `meta-ros`, a collection of OpenEmbedded/Yocto layers that add
ROS 1 and ROS 2 support to Yocto-based embedded Linux builds. It is large and
mature (~12,000 `.bb` recipes, ~3,800 `.bbappend` overrides, ~9 sub-layers
covering ROS1 Noetic; ROS2 Humble/Jazzy/Kilted/Lyrical/Rolling; SpaceROS; and
a common layer), actively maintained, and never comprehensively audited.
Produce a prioritized improvement report — not a rewrite. Do not modify
recipes or config unless asked to; this is a scan-and-report task.

## Ground truth to work from (verify, don't re-derive from scratch)

- Recipes are generated by the external `superflore` tool into `recipes-*`/
  `generated-recipes` directories; local fixes live in `recipes-bbappends*`
  as `.bbappend` files, not edits to the generated recipes directly.
- `meta-ros-common` and `meta-ros2` already use `dynamic-layers` for optional
  dependencies on `meta-qt5`, `meta-qt6`, and `meta-zenoh`.
- `LAYERVERSION_ros2-layer = "3"`; the layer.conf history comments document
  prior layer-layout versions — useful context for judging what "further
  modernization" would even mean here.
- No `AGENTS.md`, `CLAUDE.md`, or similar tool-guidance file exists at the
  repo root or in any sub-layer today.
- `.travis.yml` exists alongside a populated `.github/` — check whether CI
  actually still runs through Travis or whether this is dead config.
- `scripts/` holds maintainer tooling (`generate-skip-groups.py`,
  `ros-generate-recipes.sh`, `check-patch-files.sh`, etc.) — read these
  before assuming a gap doesn't already have partial tooling support.

## Scale constraint

Do not attempt to read all ~12,000 recipes individually. Use `grep`/`find`/
small analysis scripts to compute statistics and sample representative
examples (e.g., pick 2-3 recipes per ROS distro per finding category).
Cross-reference against `scripts/` first — several checks may already be
partially automated there.

## Areas to investigate

**1. Recipe currency & upgrade automation**
- How recipes get regenerated/updated today (trace the superflore pipeline
  referenced in the README and `scripts/ros-generate-recipes.sh`) versus
  what's manual.
- Identify `.bbappend` files that look stale: patches that may no longer
  apply cleanly, version pins (`SRCREV`/`PV`) far behind what's generated
  elsewhere, or overrides that duplicate what upstream superflore output
  would already produce.
- Any recipes still using `git://` fetch protocol where `https://`/`git+https://`
  should now be preferred (README's own "unsupported" definition flags this
  as a known category of breakage).
- Skipped-package lists (`generate-skip-groups.py` output) — are entries
  still justified, or are some now buildable upstream?

**2. Documentation**
- Gaps between what README/CONTRIBUTING cover and what a new contributor or
  downstream integrator actually needs (e.g., per-sub-layer READMEs, a
  documented recipe-override workflow, an architecture diagram of how the
  common layer + distro layers + dynamic-layers compose).
- Whether the superflore/milestone process referenced only via an external
  wiki page should be partially mirrored in-repo so it's not a single
  point of failure.

**3. AI/agent guidance files**
- Propose what a root `AGENTS.md` should contain for this repo specifically:
  the generated-vs-bbappend convention, branch model (`master`/release
  branches/`-next` branches), commit sign-off (DCO) requirement, where
  `scripts/` tooling fits, and any per-sub-layer conventions worth a nested
  `AGENTS.md`.
- Don't just recommend "add AGENTS.md" — draft the actual proposed content
  as part of the report, grounded in what you observe, not boilerplate.

**4. Yocto Project Compatible Program readiness**
- Assess against the current YP Compatible layer checklist: `layer.conf`
  correctness across all sub-layers, `LAYERSERIES_COMPAT` accuracy, license
  file presence/`LIC_FILES_CHKSUM` sanity, absence of hardcoded paths or
  network access at build time, `yocto-check-layer` tool compliance, and
  README format expectations.
- Report this as a gap list against the actual checklist, not a vague
  "probably needs work" — name which specific requirements are met/unmet/
  unknown, and what's needed to run `yocto-check-layer` locally to verify.

**5. Modernization opportunities**
- Where else, beyond the existing Qt5/Qt6/Zenoh cases, would `dynamic-layers`
  reduce hard `LAYERDEPENDS` that are actually optional per-recipe deps.
  Also check meta-ros2-humble/jazzy/kilted/lyrical/rolling for the same
  candidates.
- Whether current OE "layer template"/fragment mechanisms (e.g.,
  `template.conf`/`bblayers` fragments, or newer `bitbake-layers` layer-index
  metadata) could simplify onboarding versus the current kas-based
  instructions.
- Any other layer-layout or `bitbake` mechanism introduced in recent Yocto
  releases (check current Yocto docs) that would reduce duplication across
  the parallel ROS-distro layers.

**6. Opportunistic hygiene findings**
- CI config duplication/staleness (the `.travis.yml` question above).
- Anything else notable found while doing the above that doesn't fit a
  category — file separately, don't force-fit it.

## Output

A single written report (propose a filename/location) with findings grouped
by the six areas above. For each finding: what/where (file paths), why it
matters, estimated effort (small/medium/large), and a concrete next step.
Close with a suggested phased roadmap, since fixing everything at once
isn't realistic for a layer this size — call out which 2-3 items would give
the most value for the least effort as a starting point.
