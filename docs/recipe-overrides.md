# Fixing a Recipe

Most recipe content in this repo is generated by [superflore](https://github.com/ros-infrastructure/superflore)
from ROS's `rosdistro` metadata, not hand-written. This means you almost never
edit a recipe directly — you override it. This page walks through how.

## Step 1: find the generated recipe

Each ROS distro sub-layer (`meta-ros1-noetic`, `meta-ros2-humble`,
`meta-ros2-jazzy`, `meta-ros2-kilted`, `meta-ros2-lyrical`, `meta-ros2-rolling`,
`meta-spaceros`, `meta-spaceros-jazzy`) keeps superflore's output under its own
`generated-recipes/<package-name>/` (and some older/other `recipes-*`
directories outside `recipes-bbappends*`). Locate the `.bb` file for the
package you need to fix there first, to confirm it's generated content and to
see its exact package name and version (`PV`).

**Do not edit that file directly.** It's regenerated wholesale — see
[`AGENTS.md`](../AGENTS.md) — and any local edit is silently discarded on the
next sync.

**Exception:** `meta-ros-common` has no `recipes-bbappends` directory at all.
Its recipes are hand-maintained (not superflore-generated), so fixes there are
made directly to the recipe, the opposite of the rule below.

## Step 2: add a `.bbappend` in the matching `recipes-bbappends*` directory

Each distro layer has one or more `recipes-bbappends*` directories:

- A plain `recipes-bbappends/` for general-purpose overrides.
- Topic-suffixed variants for packages that belong to a specific stack, seen
  in this repo as `recipes-bbappends-nav2`, `recipes-bbappends-moveit2`,
  `recipes-bbappends-demos`, and `recipes-bbappends-spaceros` — used to group
  overrides for a related set of packages (e.g. every `moveit-*` override
  lives together in `recipes-bbappends-moveit2` rather than being scattered
  across per-package directories). If you're fixing a package that's part of
  an existing stack grouping, add it there; otherwise use the plain
  `recipes-bbappends`. There's no hard rule enforced anywhere for creating a
  *new* topic-suffixed directory — if your fix doesn't fit an existing group
  and you think it warrants its own, raise it with a maintainer rather than
  inventing a new top-level convention unilaterally.

Inside whichever directory applies, create a subdirectory named after the
package, then the bbappend file itself:

```
<layer>/recipes-bbappends[-<topic>]/<package-name>/<package-name>_<version-or-%>.bbappend
```

### Naming the file: prefer `_%.bbappend`

A bbappend's filename determines which recipe `PV` it applies to:

- `<package>_%.bbappend` — a wildcard that matches *any* version of that
  recipe. **Prefer this** unless your fix is genuinely version-specific.
  Example: `meta-ros2-humble/recipes-bbappends/rviz/rviz-ogre-vendor_%.bbappend`.
- `<package>_<exact-version>.bbappend` — matches only that exact `PV`.
  When superflore bumps the recipe's version on the next sync, this bbappend
  **silently stops applying** — no build error, the override just no longer
  takes effect. `scripts/rename-bbappend.sh` renames these automatically as
  part of the regeneration pipeline, but always double-check the underlying
  fix still makes sense against the new version rather than trusting the
  rename blindly.

### What goes inside

A bbappend can override any recipe variable, add patches, or adjust license
metadata. A real example, `meta-spaceros-jazzy/recipes-bbappends-nav2/ompl/ompl_1.6.0.bbappend`:

```bitbake
LICENSE = "BSD-3-Clause"

# used only as runtime dependency, but there is no ode/libode recipe...
ROS_UNRESOLVED_DEP-opende = ""

# ERROR: ompl-1.5.2-1-r0 do_package: QA Issue: ... [installed-vs-shipped]
FILES:${PN}:prepend = " \
    ${datadir}/ament_index \
"

# ERROR: ... contains symlink .so '/usr/lib/libompl.so' [dev-so]
inherit ros_insane_dev_so

# ERROR: ... contains probably-redundant RPATH /usr/lib [useless-rpaths]
DEPENDS:append:class-target = " chrpath-replacement-native"
do_install:append() {
    chrpath --delete ${D}${ros_libdir}/*${SOLIBS}
}

FILESEXTRAPATHS:prepend := "${THISDIR}/${BPN}:"
SRC_URI += "file://0001-FindPython.cmake-install_python-Allow-to-set-differe.patch"
```

Notice the pattern worth copying: **each override is commented with the QA
error or build failure it's working around.** A bbappend with no explanation
is much harder for the next person (or the next superflore regen) to judge as
still-necessary or safe to drop.

If you're adding a `.patch` file alongside the bbappend, it must:
- Include an `Upstream-Status:` line.
- Actually be referenced by the bbappend's `SRC_URI`.

Run `scripts/check-patch-files.sh <layer-glob>` yourself before submitting —
this isn't currently wired into CI (see the audit report), so nothing else
will catch a missing `Upstream-Status:` line or an orphaned patch for you.

### `SRCREV` pins (vendor packages)

Some ROS2 "vendor" packages (e.g. `mcap-vendor`, `tinyspline-vendor`,
`osqp-vendor`) only fetch release/gbp metadata by default, which does a CMake
`FetchContent` at build time — impossible in an offline Yocto build. The
standard fix is a bbappend that redirects `SRC_URI` to fetch the real upstream
project via bitbake's git fetcher, pinned with an explicit `SRCREV`, paired
with a patch that redirects the CMake `FetchContent` calls to the pre-fetched
source tree. If you write one of these, comment the `SRCREV` with the
release/tag it corresponds to (e.g. `# releases/cpp/v1.4.0`) — a bare commit
hash with no explanation is much harder to audit later.

## Step 3: common vs. distro-specific

If the fix applies to every ROS distro, check whether it belongs in
`meta-ros-common` instead (edited directly, see the exception above). If it's
specific to one distro's version of a package, keep it in that distro's
`recipes-bbappends*`.
